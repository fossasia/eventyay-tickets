Plugin Dependency Management
============================

Eventyay uses several external plugins that are pulled from separate Git
repositories.  The build system uses **two different modes** to manage
these plugin dependencies, depending on the target environment.

Build Modes
-----------

Dev / Staging (``BUILD_MODE=dev``)
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

Used when building Docker images for the ``dev`` branch and staging
deployments.

- Plugins are resolved to the **latest commit** on their configured
  branch.
- ``uv sync --upgrade-package <plugin>`` is run for each plugin,
  bypassing the lockfile pins.
- A ``CACHE_BUST`` build argument is set to a unique value (e.g. a
  Unix timestamp) so that Docker does not cache stale dependency
  layers.
- Installed plugin versions are logged in the Docker build output.

This mode is intended for active development and testing where you
want the freshest plugin code without manual hash bumps.

Production (``BUILD_MODE=production``, default)
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

Used when building Docker images for the ``main`` branch and production
deployments.

- Plugins are installed from the **pinned commit hashes** recorded in
  ``app/uv.lock``.
- ``uv sync --locked`` ensures that builds are fully reproducible.
- Plugin updates happen through an **explicit PR** generated by the
  ``update-plugin-pins`` GitHub Actions workflow.

This mode guarantees that production builds never silently pull newer
plugin commits.

How It Works
------------

Dockerfile.prod
^^^^^^^^^^^^^^^

``app/Dockerfile.prod`` accepts two build arguments:

``BUILD_MODE``
    Controls the ``uv sync`` strategy.  Defaults to ``production``.
    Set to ``dev`` for dev/staging builds.

``CACHE_BUST``
    An arbitrary value that changes between builds to invalidate the
    Docker layer cache for the dependency installation step.  Only
    meaningful when ``BUILD_MODE=dev``.

Example build commands::

    # Dev build (latest plugin commits):
    docker build \
      --build-arg BUILD_MODE=dev \
      --build-arg CACHE_BUST=$(date +%s) \
      -f app/Dockerfile.prod app/

    # Production build (locked):
    docker build -f app/Dockerfile.prod app/

CI/CD Workflows
^^^^^^^^^^^^^^^

The ``enext-docker.yml`` and ``enext-docker-pr.yml`` workflows
automatically set ``BUILD_MODE`` based on the branch:

- Pushes to ``dev`` → ``BUILD_MODE=dev``
- Pushes to ``main`` → ``BUILD_MODE=production``
- PRs targeting ``dev`` → ``BUILD_MODE=dev``
- PRs targeting ``main`` → ``BUILD_MODE=production``

Updating Production Plugin Pins
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

To update the plugin commit hashes used in production:

1. Go to **Actions → Update Plugin Pins** in the GitHub repository.
2. Click **Run workflow** (optionally enable dry-run mode).
3. The workflow will:

   a. Fetch the latest commits from each plugin's configured branch.
   b. Regenerate ``uv.lock`` with the new commit hashes.
   c. Run test collection to validate.
   d. Open (or update) a PR titled
      ``chore: update plugin dependency pins``.

4. Review the PR — it includes a table showing which plugins changed
   and the old vs new commit hashes.
5. Merge the PR to update production pins.

To enable automatic weekly updates, uncomment the ``schedule`` trigger
in ``.github/workflows/update-plugin-pins.yml``.

Plugin Version Logging
^^^^^^^^^^^^^^^^^^^^^^

Both dev and production Docker builds log the installed plugin package
versions during the build.  Look for the
``=== Installed plugin versions ===`` banner in the Docker build output
to verify which plugin commits were used.
